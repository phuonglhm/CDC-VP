# fu3_soc - FU3 SoC virtual platform

SystemC/TLM platform for FW/SW bring-up on FU3 (CVA6 application CPU + Ibex
boot/control CPU). Assembly plan: `FU3_Plan_Rap_Platform.md` (tasks T01-T28).

**Firmware baseline: [FU3_VP_ABI_1](doc/FU3_VP_ABI_1.md)** (approved
2026-10-26; C header `include/fu3_vp_abi.h`): register interfaces, SYSCSR
extension (boot status, reset cause, INTMAP enables, software IRQ), clock/
reset/boot/PMP profile, access profile and the VP/RTL difference table.

**Current state: release R1 packaged as `VP_FU3_V1.0` (plan T23): every IP of
the plan assembled (T18), image loader and command line (T20), GDB server
(T19), top-level audit and reset/wake (T21), R1 integration test matrix (T22).** The platform builds and runs
with every enabled bus target backed by a model; open points found while
assembling are listed in `plan/T08_T18_Van_De.md`.

- The bus is `fu3_bus::BusSystem` with `fu3_bus::BusConfig::fu3()`, the only
  copy of the address map: Common Spec v2.1 (`BusConfig::revision`).
- ROM (4 KiB, read-only for functional masters), CVA6_ISRAM (192 KiB image +
  4 KiB debug code), IBEX_ISRAM (64 KiB + 4 KiB) and DSRAM (256 KiB) are
  `fu3_memory` models: byte enables honoured, loader (debug) access allowed.
  Who may read, write or fetch what, and the staging/handoff switch, are the
  bus's access policy.
- CRM (`components/FU3_Components/crm`) and SYSCSR
  (`components/FU3_Components/syscsr`) are integrated; see "Clock and reset".
- Peripherals (T08-T17), all in `src/fu3_peripherals.*`, each behind its CRM
  gate and reset:
  - AP_PLIC (31 sources, Common v2.1) -> CVA6 machine external; INTMAP
    (Common v2.1 route table, per-source enables reset disabled, decision
    Q03-b) -> Ibex `irq_fast_i[14:0]`, external, software, timer; `irq_nm_i`
    has no source. Sources are shared nets: PLIC ID k+1 and the INTMAP read the
    same line.
  - TIMER0-3 (TIMER0 -> CVA6 `time_irq_i`, TIMER1-3 -> PLIC 6-8; the one-tick
    pulse is latched until software writes CMP, Q03-d), WDT0 (warning -> Ibex
    fast[0]) and WDT1 (PLIC 18); both reset requests go to the CRM watchdog
    reset.
  - Pads (`src/fu3_pinmux.*`): the 108 die pads of Common v2.1 IOPAD MAP
    (decision Q06-a; table `src/fu3_iopad_map.h` generated by
    `tools/gen_iopad_map.py` from the workbook). Each die pad carries the
    function csr_io_cfg[1:0] selects (b00 at reset). SYSCSR csr_io_cfg is not
    connected yet (Q06-b: field -> die mapping pending): the host sets the
    selects (`set_pad_select(die, select)`), as firmware will. The board
    attaches to die pads: UART peers (`kUartPad`), SPI loopback wires
    (`kSpiPad`), I2C pull-ups (dies 22/23), static levels (`set_board_pad()`);
    a board driver against a chip output is counted and reported
    (`fu3_soc/pad_contention`). JTAG, QSPI and HyperBus are modelled at
    transaction level: their pads are metadata. Die 7 (duplicate of die 8's
    mux, Q06-d pending) is not connected. The GPIO/IO_PAD components' own
    80-position IO_PAD is not used by the platform.
  - UART0-7 with a board-side `uart_line` each on their TXD/RXD die pads
    (console UART0 on dies 48/49 at b00, echoed to stdout,
    `fu3_soc_options::console_uart`); UART1 on 59/60 at b00, the others need
    their csr_io_cfg select; UART5's peer shares the I2C pads and is detached
    until `attach_uart_peer(5, true)`. Modem inputs tied inactive.
  - SPI0-3 (board loopback MOSI -> MISO die pads), I2C (open drain, board
    pull-ups, no device).
  - GPIOA/B/C: the 24 bonded pins (8 per bank) on their die pads; straps
    BOOT/MODE_1/MODE_0 from dies 2/3/4, TESTMODE/TEST_MODE_SEL from dies 5/13;
    DEBUG_EN (die 6) is a board input with no consumer (Q05-a).
  - AP_QSPIC + 16 MB flash (QSPI_XIP window), AP_HBCTRL + HyperRAM
    (HYPERBUS window, needs a bus clock fast enough for tCSM: >= PLL).
    HB_RESETN (device RESET#) follows the HYPERBUS domain reset (no HBCTRL
    CSR for it yet, Q07-a): a HYPERBUS reset also resets the device.
  - AES-256, ADC (+ `adc_macro`: per-channel stimulus `adc_input()`), RNG
    (seeded, `set_rng_seed()`), MAILBOX_IBEX/MAILBOX_CVA6.
  - AP_DMA engine on the DMA0 initiator through `fu3_bus::DmaAdapter`
    (peripheral IDs: 1 SPI0, 2 UART1, 3 UART2, 4 SPI1).
- Debug (T18): one Debug Module at IBEX_DBG (DBG reset domain) for both harts
  (`src/cpu_debug_hart.h`, hartsel 0 = CVA6, 1 = Ibex; abstract register
  access, no progbuf, no SBA); JTAG2AXI (VP JTAG profile, IR/DR level:
  `jtag()->scan_ir/scan_dr`) masters the DBG port. DM ndmreset is the CRM
  debug reset. The DBG-domain reset (watchdog, global, POR, not ndmreset)
  resets the DM and the bridge's AXI-side registers. A hart held in reset is
  reported unavailable. Ibex debug code (0x0006_0000) becomes executable only
  when the Boot ROM applies its final PMP policy (Common v2.1 Ibex-Config
  #7-#9: the reset staging region of IBEX_ISRAM is RW, no RWX); until then a
  halted Ibex loops on fetch faults at the debug exception entry.
  `fu3_soc_debug` uses a ROM stub doing that step and checks both harts run
  their debug code.
- EDHOC_OSCORE, PWM0, PWM1 and CAN (external IP for R2) are in the map but
  disabled: an access is a decode error (`TLM_ADDRESS_ERROR_RESPONSE`), like
  unmapped space. A target without a model would be bound to a
  `not_integrated_target` (`TLM_GENERIC_ERROR_RESPONSE`); none is left.
- CPU0 CVA6 and CPU1 Ibex (`components/FU3_Components/cpu`, FU3 ISS fork) are
  bound to the CVA6 and IBEX initiator ports; the CRM releases them. There is
  no image loader yet (T20).

## Clock and reset (T07)

- PRSTN (`fu3_soc_options::por_duration`, 100 ns) resets the CRM. After its
  release the CRM applies the reset filter (100 ns, spec 3.2) and the
  power-readiness qualification (255 OSC cycles = 12.75 us, spec 3.1.1), then
  its startup (spec 4.1) releases the system domain at once and Ibex 1.2 us
  later: Ibex starts 14.05 us after PRSTN rises. CVA6 stays in reset until
  software writes CRM FCLK_SW[0] = 1.
- The PLL locks 404 OSC cycles (20.2 us, CSR v2 lock counter) after power-up.
  Firmware changes the bus divider only with both selectors on the OSC
  (spec 3.7.4); the CRM reports any other sequence (`fu3_crm/clock_switch`).
- Handoff (decision Q02-b): when FCLK_SW releases CVA6, the platform first
  closes the boot staging window (`BusSystem::close_staging()`: later requests
  see the final policy, earlier IBEX requests complete) and only then releases
  CVA6. FCLK_SW = 0 / 1 resets CVA6 alone and does not reopen staging.
- Every system reset (SYSCSR `sw_reset_req`, `sw_global_rst_req`, WDT, DBG
  ndmreset) starts a new boot epoch: the bus drains and reopens staging, Ibex
  boots again from ROM, CVA6 is held (FCLK_SW cleared). The DBG reset keeps
  DBG; the others reset it too (decision Q05-e). The global request also
  resets the CRM registers. SRAM content is kept.
- Clock gates and software resets (CRM CLK_GATE_0/1, SW_RST_N_0/1) and the
  system/DBG resets apply per bus target through a `gated_target`
  (`--list-instances` shows each target's bits): a functional access to a
  gated or reset target answers `TLM_GENERIC_ERROR_RESPONSE` (decision Q02-i);
  loader/debug accesses pass. How it is reported depends on why (T21): a
  clock gate or a SW_RST_N bit while the domain runs is a software error, a
  rate-limited warning (`refused`); an access that reaches the gate while its
  domain (system or DBG) is in reset was on its way when the reset came and is
  aborted by it: counted (`aborted_by_reset`), reported at SC_DEBUG only. A
  model the reset catches with an access inside it ends that access at the
  reset, so every access caught by a reset ends before its target's domain
  is released (no access lands in a block after its reset). The run summary
  lists both counts. The gate
  also stops the IP itself (HAS 6.1): clocked models take it through their
  clock enable (`fu3_peripherals::apply_clock_gates`), keep their state while
  gated and resume when the clock returns. Reset assertion reaches a destination at once; its release is
  synchronized to the destination clock (CRM Spec V1.1 3.1.2): a release
  that comes while the destination is gated waits for the clock and then two
  more bus clock periods, so a synchronous-reset IP (UART, RNG) still sees it. QSPI_XIP
  shares the qspi bits with AP_QSPIC; UART3-UART7 use CLK_GATE_1/SW_RST_N_1
  bits 25-29 (FU3_VP_ABI_1 VP extension, not in CRM CSR v2: ABI_1 §9 #13). The
  CRM itself is never gated.
- Both CPUs run on CRM FCLK: 20 MHz OSC (50 ns per cycle) after reset,
  400 MHz (2.5 ns) once software powers the PLL (20 MHz x 20 / 1) and selects
  it (CLK_0 = CLK_1 = 1); 0 Hz stops them (decision Q01-g).
- The bus fabric runs on the CRM bus clock (`bus_clock_hz()`: the CPU branch
  divided by 2 x CLK.div, HAS 5.1 target 200 MHz for system and peripheral
  buses): every AXI stage, APB cycle and router decode takes one bus period
  (`BusSystem::set_clock`), 50 ns on the OSC after reset, 5 ns at 200 MHz. At
  0 Hz the fabric keeps its last period (the CPUs are stopped then).
- TLM global quantum `fu3_soc_options::quantum` (1 us): a CPU sees an input
  change (interrupt) at most one quantum late; WFI and resets wait on events.
- Straps boot/mode_0/mode_1/test_mode/test_mode_sel are die pads (2, 4, 3, 5, 13) driven
  by the board (`fu3_soc_options::board` at start, `set_straps()` /
  `set_board_pad()` while running). SYSCSR STATUS (0x70) reads them live
  (SYSCSR v1); FU3_VP_ABI_1 BOOT_STATUS (0x104) holds the copy captured at
  each release of the SYSCSR reset (Q05-c) and DEBUG_EN (die 6) live.
- Reset cause: `reset_history()` records POR/software/global/watchdog/debug
  for tests; firmware reads the same causes in FU3_VP_ABI_1 RESET_CAUSE
  (0x108, cumulative W1C bitmap, POR-only state).
- Software interrupts: FU3_VP_ABI_1 SWIRQ (SYSCSR 0x118-0x120) drives CVA6
  `ipi_i` and the Ibex software source.
- Not modelled: reset synchronizer latency when the destination clock runs
  and minimum reset width (the global reset ends within
  the same simulation time step: SYSCSR drops the request as soon as the reset
  starts). WDT0/WDT1 drive the watchdog reset request and the DM drives
  ndmreset; `drive_watchdog_request()` / `drive_ndmreset()` are test stand-ins
  ORed with them.

## Build

```sh
cmake -S . -B build-fu3 -G Ninja -DCMAKE_BUILD_TYPE=Release \
      -DCMAKE_C_COMPILER=/usr/bin/gcc -DCMAKE_CXX_COMPILER=/usr/bin/g++ \
      -DSYSTEMC_HOME=/opt/systemc-2.3.4 -DCDC_BUILD_FU3_SOC=ON
ninja -C build-fu3 platforms/fu3_soc/all
```

`CDC_BUILD_FU3_SOC=ON` also adds every FU3 model in
`components/FU3_Components` to the build (IO_PAD through GPIO).

## Run

```sh
VP=build-fu3/platforms/fu3_soc
$VP/vp_fu3_soc --help
$VP/vp_fu3_soc --list-instances   # targets and their state
$VP/vp_fu3_soc --self-test        # platform self-check
$VP/vp_fu3_soc --version          # package, revision, map, FU3_VP_ABI_1

# T20 console demo: Ibex ROM stub + image, straps MODE=10 BOOT=1, one console
# input line, a NOR image read through XIP, a DSRAM word dumped after the run.
$VP/vp_fu3_soc --rom $VP/fu3_t20_console.elf --mode 10 --boot-pin 1 \
    --uart-rx-file tests/data/t20_rx.txt --uart-rx-delay-us 400 \
    --flash tests/data/t20_flash.bin \
    --dump 0x0103f000:4:signature.bin --expect-uart PASS --timeout-ms 20
```

Images are preloaded before the simulation starts, through the memories'
backdoor and the QSPI NOR model (`src/image_loader.h`). This is a test preload,
outside the hardware boot flow, and not a Boot ROM: after it the platform runs
its normal power-on reset, Ibex starts at 0x0000_0080 and whatever runs from
the ROM does the rest.

| Option | Effect |
| --- | --- |
| `--rom FILE` | ROM content: an ELF (its other segments load too) or a raw image at 0x0. Required unless an `--elf` has a ROM segment: without ROM content the run stops with exit 3 |
| `--elf FILE` | every PT_LOAD segment (bss zero-filled) |
| `--load ADDR:FILE` | raw file at a system address |
| `--flash FILE[@OFF]` | raw file into the 16 MB QSPI NOR (also reachable as `--load 0x3000_0000+OFF`) |
| `--flash-out FILE`, `--dump ADDR:LEN:FILE` | NOR / on-chip memory content after the run |
| `--mode M1M0`, `--boot-pin`, `--test-mode`, `--test-mode-sel` | straps from power-on |
| `--debug-en 0\|1`, `--debug-en-release-us N` | DEBUG_EN pad from power-on, driven low at N us |
| `--pad DIE=SEL`, `--pad-level DIE=0\|1` | csr_io_cfg select of a die pad (host side, SYSCSR mapping pending), board level of a pad |
| `--console N\|none`, `--quiet-uart`, `--uart-log FILE` | console UART (default 0), echo, log |
| `--uart-rx-file FILE`, `--uart-rx-delay-us N` | bytes sent to the console RX at N us |
| `--adc CH=V`, `--rng-seed N`, `--spi-loopback N` | stimulus |
| `--timeout-ms N` (default 1000, 0 = until a verdict), `--quantum-ns N` | run length, TLM quantum |
| `--expect-uart TEXT`, `--fail-uart TEXT` | console verdict; the run stops at the end of the console line where one appears (or after 1 ms without a character). The verdict is judged on everything printed up to that stop, and the fail text wins: `PASS FAIL` in one line is a FAIL |

Preload regions (anything else is refused, as is a range crossing a region
boundary; a refused ELF writes nothing):

| Region | Range | ISA check of code |
| --- | --- | --- |
| ROM | 0x0000_0000-0x0000_0FFF | Ibex |
| CVA6_ISRAM | 0x0001_0000-0x0003_FFFF | CVA6 |
| IBEX_ISRAM | 0x0005_0000-0x0005_FFFF | Ibex |
| DSRAM | 0x0100_0000-0x0103_FFFF | none |
| QSPI_XIP (NOR) | 0x3000_0000-0x30FF_FFFF | none |

Refused: the debug partitions 0x0004_0000 and 0x0006_0000 (the Boot ROM
writes them during staging, FU3_VP_ABI_1 §6), HyperRAM (its controller must be
initialised first), MMIO and unmapped space. An ELF must be ELF32 little-endian
RISC-V. Executable segments in a CPU's region are checked against that CPU:
RVE and a hard-float ABI are refused for Ibex, a double/quad-float ABI for CVA6,
and the `.riscv.attributes` arch string may only name Ibex RV32IMC + Zicsr,
Zifencei, Zca, Zcb (Zmmul) or CVA6 RV32IMFC + Zicsr, Zifencei, Zca, Zcf (Zmmul).
An ELF without attributes is checked on its flags only; attributes that are
present but malformed (a length, string or ULEB128 running past its section
or subsection) refuse the image before anything is written.

### GDB (T19)

```sh
$VP/vp_fu3_soc --rom $VP/fu3_t19_ibex.elf --elf $VP/fu3_t19_cva6.elf \
    --gdb-cva6 3333 --gdb-ibex 3334 --expect-uart PASS
riscv-none-elf-gdb $VP/fu3_t19_cva6.elf -ex 'target remote :3333'   # CVA6
riscv-none-elf-gdb $VP/fu3_t19_ibex.elf -ex 'target remote :3334'   # Ibex
```

One GDB remote-protocol server per CPU on 127.0.0.1 (`--gdb-cva6`,
`--gdb-ibex`; port 0 picks a free one and prints it), one client each
(`src/gdb_server.h`). By default the simulation waits at time 0 until every
server has its client (`--gdb-no-wait` starts at once), and a session has no
time budget unless `--timeout-ms` is given.

- Attach halts the hart at its next instruction; a hart held in reset (CVA6
  until the handoff) halts on its first instruction after the release, and
  GDB's first stop reply waits for it (`set remotetimeout` if that is long).
- Stop = RISC-V Debug Mode of the ISS: halt request, `stepi` (dcsr.step,
  interrupts masked), `break` (EBREAK patched into memory, dcsr.ebreakm/u),
  `hbreak` (execute triggers: CVA6 2, Ibex 4), ^C. No watchpoints (Q04-e).
  Software breakpoints cannot go into the QSPI XIP window, and code copied
  over one (Boot ROM staging) removes it: use `hbreak` there.
- Registers: x0-x31, pc (= dpc), CVA6 f0-f31 with fflags/frm/fcsr, and
  mstatus, misa, mie, mtvec, mscratch, mepc, mcause, mtval, mip, mcycle,
  minstret, mhartid. dcsr, dpc and the trigger CSRs belong to the stub.
- Memory: the hart's own bus port as a debug transaction (bus map, no access
  policy, no side effects, no simulated time); an unmapped address or a target
  without debug access answers an error.
- A reset of the hart while GDB is attached halts it on its first instruction;
  the stub re-arms dcsr and the triggers and lets it continue unseen by GDB.
- Simulated time stands still while every attached hart is stopped: the whole
  SoC (timers, watchdogs, the other CPU when it has no client) waits for the
  debugger. While one attached hart runs, the server polls every 10 us of
  simulated time, so a stop is reported up to 10 us later (the hart itself is
  halted at once).
- `detach` (or a closed connection) removes the breakpoints, restores dcsr
  and lets the hart run; `kill` also ends the run (exit 0, "run ended by a
  GDB kill").
- A packet with a wrong checksum is never executed: the server answers `-`
  (acknowledgement mode, GDB resends it) or drops it in no-ack mode, and
  reports it; a `-` from the client gets the last packet again.
- One owner per hart (decision Q04-d): the Debug Module (JTAG, T18) and GDB
  share `cpu_debug_hart`. While GDB owns a hart the DM sees it unavailable and
  cannot halt, resume or access it; while the DM has it halted (or a halt
  request set) a GDB attach is refused (the connection is closed, the reason
  printed). A DM halt request set meanwhile applies at GDB detach.

Exit status: 0 pass (`--expect-uart` text seen, or the time budget ended
without a verdict asked), 1 fail (`--fail-uart` text, self-test failure),
2 timeout (`--expect-uart` text not seen), 3 simulator, integration or image
error, 4 usage error. `--trace` prints every routed bus transaction,
`--verbose` sets SystemC verbosity to `SC_DEBUG`.

The self-test takes the free IBEX initiator port and checks the assembled
platform, not any model: each target decodes to its own model (a debug read of
a register with a known reset value; QSPI_XIP, HYPERBUS and AP_DMA have no
such probe), a bus path still holding a not-integrated responder returns its
error (none is left), and unmapped space returns a decode error.

`test_fu3_soc_cpu` loads the image with the debug loader, lets the platform
boot it and reads the verdict from a DSRAM mailbox (`tests/fw/fw_common.h`): the firmware
asks for interrupt causes (bits 0-30) and the debug request (bit 31) through
it. The mailbox is a test convention, not an ABI; the harness drives the CPU
interrupt and debug inputs directly (the peripherals stay idle in that test).

The CLI tests run through `tests/expect_exit.cmake`, which fails on a wrong
exit status as well as on missing output (`PASS_REGULAR_EXPRESSION` alone
ignores the exit status) and, with `CHECK_FILE`, on the bytes of a file the
run writes (removed first). `ctest -L fu3_cli` runs the T20 set.

`--list-instances` and `--version` print the map revision from
`BusConfig::revision`, so a copied table always says which spec it follows.

## Package (T23)

```sh
cmake -S . -B build-pkg -G Ninja -DCMAKE_BUILD_TYPE=Release \
      -DCMAKE_C_COMPILER=/usr/bin/gcc -DCMAKE_CXX_COMPILER=/usr/bin/g++ \
      -DSYSTEMC_HOME=/opt/systemc-2.3.4 -DCDC_BUILD_FU3_SOC=ON -DFU3_SOC_PACKAGE_NAME=VP_FU3_V1.0
ninja -C build-pkg -k 0; mkdir -p build-pkg/ship && (cd build-pkg && ctest -L fu3 > ship/ctest_fu3.log)
TEST_LOGS=build-pkg/ship SPEC_DIRS=<spec dirs> GDB=<riscv-none-elf-gdb> \
    platforms/fu3_soc/tools/make_package.sh build-pkg <fx1>/vp VP_FU3_V1.0
```

`tools/make_package.sh` assembles the fx1-style package (`vp/bin|configs|doc/
VP_FU3_V1.0`, a section in `vp/licenses/README.md`): binary and SystemC runtime
(RPATH `$ORIGIN`), the example images with their sources, the documents of
`doc/package/` (guide, interrupt/DMA map, ISA, clock/reset, R1 gaps, CSR index)
with FU3_VP_ABI_1, the bus map printed by the binary, the IP register headers,
the regression logs, then runs the package's own checks
(`tools/package/run_package_tests.sh`, shipped in `configs/`) and writes
`MANIFEST.txt` (revisions, source and spec fingerprints, sha256 of every file).
It refuses to replace an existing package unless `FORCE=1`.

# Running and evaluating a network through the system wrapper

This guide is for software that drives the NPU model through the system wrapper (`npu_tlm`) with extended
instructions, and wants (a) results that match the reference bit for bit and (b) performance figures, including the PE
utilization. It complements `SW_INTEGRATION_GUIDE.md` (register map, programming sequences, data preparation), which
remains the reference for every field named here.

Addresses are offsets inside the NPU window of the wrapper unless a line says "model address". A model address
`0x400003xx / 0x400004xx` maps to the wrapper offset `0x10000 + (model address - 0x40000000)`; for example the push
register `0x40000310` is `0x10310`.

## 1. Which path is verified

| Path | Engine behind it | Use for network evaluation |
|---|---|---|
| Extended instructions (alias `0x10000`, push at `0x10310`) | `HasNpuTop`: RTL-accurate core, tiling, DMA, epilogue, vector unit | Yes. YOLOv8m (98 instructions) and ViT-B/16 (244 instructions) match the reference on every instruction through the wrapper (`VERIFICATION_REPORT.md`, V20) |
| Register-file window of the DFC (model `0x40000800`, push `0x17` at `0x10310`; on by default, `HAS_HOST=v45` switches it off) | `HasNpuTop`, after the image of 82 words is decoded back into a layer and checked against the hardware | For programs meant for the hardware: only the layers the hardware runs as written are accepted; a refused layer is still reported as done by the wrapper, read `0x10318` and `0x1031C` after every layer (`NEO_REGISTER_FILE.md`, section 2.2; `COMPILER_GUIDE.md`) |
| GEMM bank (`0x30000`) | Native array, one 32 x 32 tile, raw int32 result, no epilogue | No. Results and cycle counts do not relate to the reference programs |

The verification above was done with the programs of the data package (`has/insts_pe3`, `has/vit_full`, `has/rce_gate`),
which the front end of this package generated. A program generated by another compiler is only covered by the checks of
sections 4, 5 and 7.

## 2. Checklist for one run

1. Place the DRAM image (`dram_init.bin`) in system RAM, outside the code, stack and heap of the firmware. The image
   holds the quantized input, the weights, the biases and every table.
2. Write the physical address of the image to `RICH_WINDOW_BASE` (`0x31130`) and its size to `RICH_WINDOW_SIZE`
   (`0x31134`) before the first extended instruction. The whole window must lie in `0x80000000..0x8FFFFFFF`.
3. For every instruction, in program order:
   - write its registers; every register write of the instruction must be done before its push;
   - **add the address of the image to all 13 address registers**: the 8 parameter registers at model addresses
     `0x400, 0x404, 0x408, 0x40C, 0x434, 0x444, 0x448, 0x44C` and the 5 extension registers `0x490, 0x494, 0x498,
     0x4E0, 0x4E4` (in `mmio.txt` these values are offsets in the image; a value of 0 stays 0);
   - push the opcode at `0x10310` (lane A);
   - wait for the DONE bit (bit 1) of the wrapper's `STATUS` (`0x30004`), then clear it by writing the bit;
   - run the checks of section 4 before the next instruction.
4. Run the host steps of the program (lines starting with `H` in `mmio.txt`; YOLOv8m has two `upsample2x` steps) on
   the RAM, at their place in the sequence.
5. Read the results from RAM (section 3).

Rules that are easy to miss:

| Rule | Why |
|---|---|
| One instruction at a time: never push while the previous instruction runs | Every push of an extended instruction copies the whole window from RAM into the model again; a push during a run overwrites the output being written |
| The parameter registers `0x400..0x468` keep their values; the extension registers `0x46C..0x500` are cleared by every push | A program writes only what changes in the first range, and everything it needs in the second range, for every instruction |
| An instruction that writes no extension register goes to the functional decoder, not to `HasNpuTop` | Its arithmetic is different. Measured on `tools/has/make_ref_gate.py`: an ELEM_WISE ADD with real-valued scales and no extension register gives 2,288 of 2,304 bytes different from `HasNpuTop`, and reports 0 cycles |
| Read outputs only after DONE of the wrapper | The wrapper copies the window back to RAM when the instruction has finished |
| The CPU must not write inside the window while an instruction runs | The copy-back overwrites the whole window |
| Do not set `HAS_*` or `SAURIA_CORE_RTL_*` environment variables unless a comparison asks for it | The model reads them at construction; they change cycle counts and, for some, values |
| A soft reset clears the window registers | Write them again |

### 2.1 What breaking the two timing rules does

Measured through the wrapper, on purpose, with the 14-instruction transformer program and the first instructions of a
ViT-B/16 block. None of these cases raises an error: every instruction retires and the status registers look normal.

| Case | Result |
|---|---|
| The CPU writes 16 bytes into the window while an instruction runs | After DONE the bytes hold their values of the push time: the write is lost. The same write made between two instructions is kept |
| The next instruction is pushed right after the previous push, without waiting | Accepted (the model reports busy with one instruction queued). Both outputs are correct |
| FUSED_ATTN of about 40 microseconds; the next instruction is pushed 10, 20 or 25 microseconds into it | Both outputs are correct |
| The same, pushed 30 or 35 microseconds into it | 12,402 of the 12,608 output bytes of the running instruction are wrong; the pushed instruction is correct |
| Convolution with 216 tiles (about 670 microseconds); the next instruction is pushed 5 microseconds into it | Both outputs are correct |
| The same, pushed 150 microseconds into it | 122,656 of the 453,888 output bytes of the convolution are wrong, and so are 11,987 of the 12,608 bytes of the next instruction, which reads them |

What happens: the model works on a private copy of the window. A push reloads the whole copy from RAM; the wrapper
copies the whole window back to RAM after every instruction that retires (its DONE bit rises only when no instruction
is left). A push therefore replaces everything the running instruction has already written into the copy by the old RAM
contents. An early push goes unnoticed only when it arrives before the first output byte: FUSED_ATTN writes its output
in one piece after its products, a convolution writes tile by tile from the first tile on, ELEM_WISE writes chunk by
chunk. Software that does not wait for DONE gets results that are right or wrong depending on timing.

## 3. Where the results are

Every instruction writes its output tensor at its `OUT_ADDR` (model address `0x40000408`) inside the image; there is no
separate output area. Software reads RAM at `image address + OUT_ADDR`.

Layout: int8, C order `[c][h][w]`. A flattened 1 x 1 layer has `h = 1`, `w = H * W` (the same bytes as `[c][H][W]`).
Transformer tensors are channel-major `[dim][token]`. Some LAYERNORM instructions write int16 (twice the bytes), as their
parameter block says.

Final tensors of the two reference programs:

| Network | Instruction | Tensor | `OUT_ADDR` (offset) | Shape | Bytes |
|---|---:|---|---:|---|---:|
| YOLOv8m | 82 | box, stride 8 | `0x346AC00` | `[64][80*80]` | 409,600 |
| YOLOv8m | 85 | box, stride 16 | `0x3500C00` | `[64][40*40]` | 102,400 |
| YOLOv8m | 88 | box, stride 32 | `0x3526400` | `[64][20*20]` | 25,600 |
| YOLOv8m | 91 | class, stride 8 | `0x3784800` | `[80][80*80]` | 512,000 |
| YOLOv8m | 94 | class, stride 16 | `0x3897800` | `[80][40*40]` | 128,000 |
| YOLOv8m | 97 | class, stride 32 | `0x38DC400` | `[80][20*20]` | 32,000 |
| ViT-B/16 | 243 | logits | `0x6BEC800` | `[1000][197]`, the class token is column 0 | 197,000 |

The YOLOv8m program stops at these six int8 tensors. Box decoding (DFL, sigmoid, NMS) runs on the CPU;
`tools/fe/fe_sysc_detect.py` and `tools/fe/fe_vit_top5.py` do it for the reference programs and need the quantization
scales of the program directory. The input image is part of `dram_init.bin`: another image needs another program.

## 4. Checks after every push

The wrapper reports DONE for an instruction that the model refused, because a refused instruction never enters the
queue. Software must look at the status registers of the model itself.

| Check | Register | Expected |
|---|---|---|
| The instruction was accepted | `RICH_STATUS` (`0x10318`) bit 2 (sticky error) | 0. When 1, bits 31..16 hold the error code; write the register to clear it |
| The instruction retired | `RICH_RETIRED` (`0x1031C`) | grows by exactly 1 per instruction |
| The instruction did work | `PERF_EXEC_CYCLES` | not 0 and plausible for the layer |

Error codes of `RICH_STATUS`:

| Code | Name | Meaning |
|---:|---|---|
| 1 | `Q_OVF` | Queue full |
| 2 | `LANE_B` | Push on lane B: not supported on this path |
| 3 | `LEGACY64` | 64-bit instruction interface: not supported |
| 4 | `UNSUPPORTED_OP` | Opcode other than `0x05`, `0x12` to `0x15`, `0x16` (`DMA_TENSOR`) and `0x17` (doorbell of the register-file window); also a layer refused at that doorbell |
| 5 | `UNSUPPORTED_MODE` | Activation type above 3, or an ELEM_WISE mode other than ADD, MAX_POOL, AVG_POOL, slice, concat, upsample, reshape (modes 6 to 9, by default); `DMA_TENSOR` `MODE_PACK` other than 0, 2, 3 |
| 6 | `BROADCAST` | ELEM_WISE ADD with operand lengths that differ |
| 7 | `NEED_LUT` | Activation 2 or 3 without `LUT_ADDR` |
| 8 | `BAD_GEOM` | Sizes that do not fit together, `TILE_CIN` that does not divide `IN_C`, `Y_USED` above 32, missing `PARAM_ADDR` |
| 9 | `SCALE_RANGE` | A real-valued scale that cannot be converted |
| 10 | `NO_TILING` | Tile sizes missing |
| 11 | `SWEEP` | Positions per context x stride too large for the feeder (`SW_INTEGRATION_GUIDE.md`, error 11): choose a smaller `Y_USED` |

Conditions that the model detects during a run but that software **cannot read from a register of the wrapper**: a
tile whose weights do not fit the weight SRAM (the instruction writes no output), a core pass that does not finish, a
wrong FUSED_ATTN / LAYERNORM parameter block (the instruction writes no output), an epilogue configuration error. In
the output they only show as wrong bytes, which is why the comparison of section 5 is done per instruction. The model
root reports them on stderr (section 4.1), and the testbench `tools/has/tb_has_npu_top` prints the counters when it
replays a program directory.

### 4.1 Warning lines of the model root

The model root `core_rtl/` prints a line on stderr of the simulation, without any option, in three cases
(`SAURIA_CORE_RTL_WARN=0` switches them off):

| Line starts with | Meaning |
|---|---|
| `[core_rtl] WARNING: push N (opcode ..) refused by HasNpuTop: error C NAME` | The N-th extended instruction was refused (codes of the table above). It does not run, although the wrapper reports DONE |
| `[core_rtl] WARNING: push N ...: no integer scale registers written` / `... a default tiling was chosen` | The instruction runs, but with converted real-valued scales (an approximation) or with a tiling chosen by the model: registers that a compiler is expected to write are missing |
| `[core_rtl] WARNING: push N (opcode ..): the weights (W_ADDR) at 0x.., .. bytes, ends beyond the DRAM image area` (also for the input and output tensors, bias, scale, shift, activation table, skip tensor, ELEM_WISE operands, FUSED_ATTN and LAYERNORM tensors) | A region the instruction reads or writes ends beyond the image area of the model (`0x10000000` bytes). Printed at the push, before the instruction runs, so the line is in the log even when the simulation then crashes. A bus address that was not converted to an image offset is pointed out |
| `[core_rtl] WARNING: push N (opcode 0x12): a tile of TILE_COUT .. x TILE_H .. x TILE_W .. (TILE_CIN ..) does not fit the SRAMs of the hardware (over: ..): input window .. bytes (limit 80896), weights .. bytes (limit 82944), partial sums .. (limit 24576). The model runs it all the same; results may be wrong` | One tile of the instruction needs more than one buffer of SRAM-A (input window, 80,896 bytes), SRAM-B (weights, 82,944 bytes) or SRAM-C (24,576 partial sums); the line names the SRAMs that are exceeded after `over:` and gives the three sizes. Printed at the push. The model runs the instruction all the same: the hardware could not, and the result of the model may be wrong (`TILING_GUIDE.md`, section 3) |
| `[core_rtl] WARNING: instruction N retired with internal errors` | The N-th retired instruction raised an internal error counter; the line names the counters. Its output may be missing or wrong |

Measured through the wrapper on the transformer program: no line on a correct run; a refused instruction (a length of
0) and an overwritten parameter block each give their line.

### 4.2 Recording a program

With `SAURIA_CORE_RTL_RECORD=<directory>` the model root writes the program that reaches `HasNpuTop` to
`<directory>/segNNN/`, in the program-directory format of this package:

| File | Content |
|---|---|
| `mmio.txt` | The register writes and pushes as `HasNpuTop` receives them: addresses are offsets in the image |
| `dram_init.bin` | The image at the first push of the segment |
| `dram_golden.bin` | The image after the last instruction of the segment, as this run produced it. It is not an independent reference |
| `<directory>/record.csv` | One line per retired instruction (cycles, `ok` or `errors`) and per refused push |

A new segment starts whenever the image changed between the end of an instruction and the next push, that is at every
step the CPU does on the data. The image is recorded up to its last non-zero byte and to the highest address written to
an address register. The recording does not change results or cycle counts; it writes the image once per instruction.

`tools/has/tb_has_npu_top <directory>/segNNN` replays a segment without the wrapper and prints the internal error
counters. Measured: the recording of the 14-instruction transformer program replays with all outputs equal and the same
285,205 cycles (with the vector-unit knobs at 0 (the configuration of the package check: `HAS_GVU_TOP=0 HAS_GVU_STALL=0 HAS_GVU_ELEM_CLK=0 HAS_GVU_REGS=0 HAS_GVU_AGU_ND=0`, the four operation knobs `HAS_GVU_AVG`, `HAS_GVU_SOFTMAX`, `HAS_GVU_FA`, `HAS_GVU_LN` at 0, and `HAS_DMA_TENSOR=0 HAS_DMA_ND=0`); with the default of this package the recording was not replayed; the same program gives 263,808 cycles through the wrapper). On a segment that contains a refused push the testbench prints a `REFUSED` line with the error code for
that instruction, checks the others and ends with FAIL.

## 5. Comparing with the reference

Compare **every instruction in order**, not only the final tensors: the first instruction that differs points at the
cause. One `dram_golden.bin` holds the correct output of every instruction, because every tensor has its own region in
the image.

| Tool | What it does | Needs |
|---|---|---|
| `tools/has/wrapper/test_npu_tlm_core_rtl <program dir> [count or all]` | Builds the real wrapper with a bus and a memory, replays the program, compares the output of every instruction with `dram_golden.bin`, prints the cycles and the PE utilization of every instruction | The wrapper sources and the model root `core_rtl/`. Start with `has/rce_gate` (14 instructions), then the first instructions of `has/insts_pe3`, then a whole network |
| `tools/has/wrapper/fw/` (`npu_has_fw.c`, `make_fw_program.py`) | C99 firmware that replays a program and checks a CRC-32 of every output; no reference image inside the firmware | A CPU on the platform. This firmware has run on the host through the wrapper, not yet on a CPU model |
| RAM dump compared with `dram_golden.bin` | Region by region, in instruction order | A way to dump RAM after the run |
| `tools/has/ref_program.py <program dir>` | Computes the output of every GEMM_FUSED and ELEM_WISE instruction from `mmio.txt` and `dram_init.bin` with plain integer arithmetic, independent of the model, and compares it with an image (section 5.1) | Python 3 with numpy |
| `tools/has/tb_has_npu_top <program dir>` | Replays the program without the wrapper; the source of the reference numbers; prints `[STEP] ... bad=N PASS/FAIL` per instruction and every internal error counter | The model only |

Cycle counts: compare with the reference run of the **same model release**. Per instruction, `PERF_EXEC_CYCLES` through
the wrapper equals the cycles of `tb_has_npu_top` for that instruction. ViT-B/16 reaches its reference cycle count with
`SAURIA_CORE_RTL_C_BCAST=1`.

### 5.1 A reference for a program that has no reference image

`dram_golden.bin` exists only for the programs of this package. For a program from another compiler, a recording
(section 4.2) holds the image the model produced, which is not a reference. `tools/has/ref_program.py` gives one: it
reads the registers of every instruction, takes the tensors, weights, biases, scales and tables from the image and
computes the output as one sum over the whole tensor. It shares no code with the model and uses the tiling registers
only to find the weights of each output-channel range.

```
python3 tools/has/ref_program.py <dir>/seg000                      # a recording: model result against the reference
python3 tools/has/ref_program.py <program dir> --image ram.bin     # a RAM dump against the reference
python3 tools/has/ref_program.py <program dir> --write-ref ref.bin # the reference image, to compare with the framework
```

It prints one line per instruction (`MATCH`, `MISMATCH` with the first element that differs, `REFUSED` with the error
name, `NOT CHECKED`) and notes on what the registers imply: a missing `SCALE_ADDR`, `BIAS_ADDR = 0`, a tile that does
not fit the hardware, a partial sum outside int32. After a mismatch it continues from the output of the image under
test, so every instruction is judged on its own (`--no-resync` switches this off). `--first F --count N` checks a
window. `--addr-base` subtracts a bus address from the address registers when the program holds bus addresses.

How to read the result:

| Model against this reference | Program against the framework | Meaning |
|---|---|---|
| MATCH | equal | The program is right and the model ran it right |
| MATCH | different | The registers or the data of the program do not describe the intended layer: weight order, bias, scales, tiling of the weights (section 7) |
| MISMATCH | - | The model did not compute what the registers say: send the recording (section 9) |

Measured: the 98 instructions and 2 host steps of YOLOv8m match the reference image (58,425,600 elements); of ViT-B/16
the 75 GEMM_FUSED and ADD instructions match (20,470,664 elements) and the 169 FUSED_ATTN and LAYERNORM instructions are
not checked; the AVG_POOL check program matches (8 instructions); a recording made through the wrapper matches. Faults
planted in one instruction of YOLOv8m are reported on that instruction only: one output byte, one weight byte, the shift
of one channel (232 elements), the bias of one channel (382 elements), weights of a range stored in another order
(11,520 elements). The instruction forms that the networks do not use have their own check program
(`tools/has/make_ref_gate.py`: a real-valued scale without `SCALE_ADDR`, the residual form `HAS_SKIP`, an instruction
without extension registers, ADD with real-valued scales, a table activation with a last channel range shorter than
`TILE_COUT`): on three random data sets the image the model produces equals the reference on all six instructions
(17,536 elements each), and the same program written with bus addresses gives the same result with `--addr-base`.
FUSED_ATTN and LAYERNORM are not computed. No program from another compiler has been run.

`--write-ref` writes the reference alone (it implies `--no-resync`). An instruction without extension registers reads its
input as `[K][1][M]`, the layout of every other tensor; `tools/has/tb_has_npu_top` does not compare the output of such
an instruction, this tool does.

## 6. Performance figures

The wrapper clears the counters at every push, so every figure is per instruction; software adds them over the
network. `CYCLE_COUNT` of the GEMM bank is not updated by extended instructions.

| Figure | How |
|---|---|
| Cycles of the network | Sum of `PERF_EXEC_CYCLES` over the instructions |
| Frames per second | Clock frequency / that sum |
| Where the time goes | `PERF_DMA_ENGINE_CYCLES` (waiting for the DMA), `PERF_OBP_CYCLES` (epilogue), `PERF_POOLING_ENGINE_CYCLES` (ELEM_WISE), `PERF_REDUCTION_ENGINE_CYCLES` (FUSED_ATTN, LAYERNORM) |
| Bus traffic | `PERF_DDR_READ_BYTES`, `PERF_DDR_WRITE_BYTES` |
| PE utilization of an instruction | `PERF_ACTIVE_PE_CYCLES / PERF_TOTAL_PE_CYCLES` |
| PE utilization of the network | Sum of `PERF_ACTIVE_PE_CYCLES` / sum of `PERF_TOTAL_PE_CYCLES` over the instructions |
| Tiles per instruction | Run with `SAURIA_CORE_RTL_TRACE=1` and read the `[DFC]` lines on stdout |

Definition used for extended instructions: `PERF_ACTIVE_PE_CYCLES` is the number of real multiply-accumulates of the
layer (output elements x input channels x kernel height x kernel width); `PERF_TOTAL_PE_CYCLES` is the core busy cycles
x 1,024, the core being busy from the start pulse of a pass to its done. ELEM_WISE and LAYERNORM do not use the array and
add nothing. A model release that predates these counters leaves both at 0 for extended instructions: check that
`PERF_TOTAL_PE_CYCLES` is not 0 after a GEMM_FUSED instruction before using the ratio.

Measured on the model: the core busy count is 2 cycles per core pass above the count of the instrumented build (0.06 %
on a YOLOv8m window of 432 passes); through the wrapper the ratio read from the two registers equals the one of the
testbench on the 14-instruction transformer program.

### 6.1 Report file of a run

`SAURIA_CORE_RTL_REPORT=<file>` makes the model write the figures above itself, without firmware reading registers after
every instruction. It changes no result and no cycle count.

| File | Content |
|---|---|
| `<file>` | CSV, one line per instruction that `HasNpuTop` retired, in order: operation, geometry and tiling registers, output elements, cycles, cycles so far, tiles, core passes, core busy cycles, real multiply-accumulates, PE utilization, cycles waiting for the DMA, epilogue cycles and its configuration cycles, ELEM_WISE cycles, FUSED_ATTN / LAYERNORM cycles, bytes read and written on the bus, `ok` or `errors`; then the padding the instruction uses on each side (`pad_t`, `pad_l`, `pad_b`, `pad_r`: `PAD_T` ... `PAD_R` when any of them is written, else `PAD`), `pad_value` and `dilation` (1 when not written and for a 1x1 kernel). The column `pad` keeps the value of the `PAD` register |
| `<file>.summary.txt` | Totals of the run so far: instructions retired, pushes refused, pushes with a region beyond the image area, pushes with a tile above the SRAM limits, instructions with errors, cycles, clock period, time, frames per second, PE utilization, shares of the core / DMA wait / epilogue, tiles, core passes, bus bytes, cycles per operation. Rewritten after every instruction, so it is complete however the simulation ends |

The column `instruction` counts the instructions `HasNpuTop` retired (the value of `RICH_RETIRED`), not the pushes: a
refused push and an instruction that goes to the functional decoder have no line. Layer names are not known to the model;
join by order with the program. The frames per second use the clock that drives the model in the platform and assume
one run of these instructions per frame; the steps the CPU does between instructions (the two `upsample2x` of YOLOv8m)
and the copies the wrapper makes between RAM and the model are not in any of these numbers.

Measured through the wrapper with the vector-unit knobs at 0 (the configuration of the package check: `HAS_GVU_TOP=0 HAS_GVU_STALL=0 HAS_GVU_ELEM_CLK=0 HAS_GVU_REGS=0 HAS_GVU_AGU_ND=0`, the four operation knobs `HAS_GVU_AVG`, `HAS_GVU_SOFTMAX`, `HAS_GVU_FA`, `HAS_GVU_LN` at 0, and `HAS_DMA_TENSOR=0 HAS_DMA_ND=0`); the default of this package gives
263,808 cycles through the wrapper): on the 14-instruction transformer program the lines add up to 285,205 cycles and the
summary gives 23.18 % PE utilization, the values the wrapper test reads from the registers; every line equals
`PERF_EXEC_CYCLES` of its instruction; a program with a refused push reports 13 lines and 1 refused push; with and
without the report the run gives the same outputs and cycles. Not yet run on a whole network.

## 7. Programs from another compiler

Nothing below raises an error: a violation gives different output bytes. `SW_INTEGRATION_GUIDE.md`, section 6, has the
full description.

| Point | What the model requires |
|---|---|
| Weight order | SAURIA order per output-channel range: the range starting at channel `c0` sits at `W_ADDR + c0 * K`, laid out `[c][kh][kw][k]`, `K = KH * KW * IN_C`. A row-major `K x N` matrix does not work |
| Weights with an input-channel split (`TILE_CIN < IN_C`) | Every output-channel range is stored as `IN_C / TILE_CIN` consecutive parts; part `j` at `W_ADDR + c0 * K + j * nch * Kt`, `Kt = KH * KW * TILE_CIN` |
| `PAD_TAIL` (FLAGS bit 0) | The compiler pads the last output-channel range with zero weights up to `TILE_COUT`. Setting the flag without padding reads past the weights |
| Bias | int32 per output channel at `BIAS_ADDR + 4 * c`, always read. With `BIAS_ADDR = 0` the first bytes of the image are used as bias |
| Scale and shift per channel | Two 32-bit arrays at `SCALE_ADDR` and `SHIFT_ADDR`, indexed by the absolute channel. Without `SCALE_ADDR` the model converts the real-valued scales, which is an approximation and does not match an integer reference bit for bit |
| Activation table | `ACT_TYPE` 2 and 3 need `LUT_ADDR`: 256 entries, entry `x` for the input value `x - 128` |
| Tiling | `TILE_COUT`, `TILE_H`, `TILE_W` present; weights of a tile at most 82,944 bytes (otherwise the tile is dropped and the instruction writes no output). The input window and the output of a tile must also fit their SRAMs (`TILING_GUIDE.md`): the model warns at the push when a tile exceeds one of the three limits (section 4.1) and runs the instruction all the same. A tile beyond what the model itself can hold is cut at that size and the instruction retires with internal errors |
| Geometry | One `STRIDE` for both directions; dilation `DILATION` (1 when not written; `(KW - 1) x DILATION` at most 63). Padding: `PAD` on all four sides, or `PAD_T`, `PAD_L`, `PAD_B`, `PAD_R` per side; the padded positions hold `PAD_VALUE` (0 when not written) |
| Signed values | Zero points and shifts are written as 32-bit two's complement words |
| Addresses | The model does not stop an access outside the image: it warns at the push when a region ends beyond its image area (section 4.1) and runs the instruction all the same. Regions inside that area but outside the window of the wrapper are not detected |
| ELEM_WISE ADD | `A_LEN = B_LEN = LEN`; the integer parameters are used only when `SA` is written |
| FUSED_ATTN, LAYERNORM | Parameters come from the block at `PARAM_ADDR` in the image, not from registers; set FLAGS bit 1 for channel-major tensors |

To separate "the compiler generated something else" from "the run went wrong": record the run (section 4.2), or export
the program in the directory format of this package (`mmio.txt` with offsets in the image, and `dram_init.bin`), and
replay it with `tools/has/tb_has_npu_top`. The replay prints the internal error counters that the wrapper does not show, and with
`FE_SNAPSHOT_DIR` set it writes the image after the run for comparison with the result the compiler expects.

## 8. Common causes of a mismatch

| Symptom | Likely cause |
|---|---|
| Every convolution differs, no error | The image is not at `0x80000000` and the image address was not added to the 5 extension address registers |
| An output holds old data | Read before DONE of the wrapper, or the next instruction was pushed too early |
| Results change from run to run, or with the speed of the firmware | The next instruction is pushed while the previous one runs (section 2.1) |
| Everything after the neck of YOLOv8m differs | The two `upsample2x` host steps were skipped |
| DONE but nothing changed | The instruction was refused: `RICH_STATUS` bit 2 (section 4) |
| `BAD_GEOM` / `NO_TILING` on an instruction that looks unchanged | Extension registers were not written again; every push clears them |
| A push or a register write is refused by the bus | Window registers missing, window outside `0x80000000..0x8FFFFFFF`, or an address register outside RAM |
| Firmware crashes after an instruction | The window overlaps firmware memory; the copy-back writes the whole window |
| Values match, cycles differ | Reference table of another model release, or an environment variable is set |
| Decoded boxes or classes are wrong while the bytes match | Layout of the outputs (section 3): int8, not dequantized, `[C][H*W]` |

## 9. What to send when a comparison fails

1. The model release (commit of the model tree in the platform) and the environment variables that were set.
2. The program: a recording made with `SAURIA_CORE_RTL_RECORD` (section 4.2), or `mmio.txt` and `dram_init.bin` in the
   directory format; the stderr of the simulation (warning lines of section 4.1); and the output of
   `tools/has/ref_program.py` on it (section 5.1).
3. The number of the first instruction that differs, its opcode, and `RICH_STATUS`, `RICH_RETIRED`, `PERF_EXEC_CYCLES`
   read after it.
4. Where the image was placed and how the 13 address registers were written.
5. Which host steps ran between instructions.

## 10. Limits of this guide

- The wrapper path was verified with a SystemC test program on the host. No run with firmware on a CPU model of a
  platform has been made.
- The one-push-at-a-time rule and the copy-back of the whole window were reproduced on purpose (section 2.1). Two
  further points were derived from the source code and not exercised: the five extension registers that hold addresses
  are neither checked nor translated by the wrapper, and the window is transferred to and from system RAM as a single
  bus transaction.
- A platform with another memory map, another bus or an interrupt controller needs its own check of the window
  placement (the wrapper accepts `0x80000000..0x8FFFFFFF` only), of the transfer of the whole window in one bus
  transaction, and of bus errors, which such a platform may turn into traps.

## Executive Summary & Answers to Core Milestone Questions

This technical document serves as the formal engineering milestone completion report for the **SAURIA FX1 (v4.4 SoC / v4.2 NPU Core)** cycle-approximate SystemC virtual prototype and automated AI compiler infrastructure. The report explicitly addresses the three fundamental questions governing the completion of this architectural phase:

### 1. What has been developed?
A complete, modular, header-only SystemC cycle-approximate virtual prototype modeling the dual-lane **SAURIA FX1 NPU Core**. The hardware implementation includes:
* **Dual-Lane Symmetric Processing Core**: Two independent execution lanes (**Lane A** and **Lane B**), each housing a $32 \times 64$ Processing Element (PE) systolic array grid (totaling 4,096 MAC units across the chip).
* **64-bit Rich Instruction Set Architecture (ISA)**: A specialized, compact control format featuring five primary opcodes (`SET_NSPLIT`, `GEMM_FUSED`, `FUSED_ATTN`, `LAYERNORM`, and `ELEM_WISE`) submitted via dedicated dual asynchronous hardware queues (`Queue A` and `Queue B`).
* **Output Post-Processing Block (OBP Epilogue Engine)**: A dedicated 4-stage post-processing pipeline per lane (processing 64 parallel channels in SIMD fashion) that fuses Bias Addition, Requantization, 16 KB Activation SRAM LUT lookups, and Residual Skip Additions directly into the memory writeback path.
* **Dual Reconfigurable & Reduction Subsystem (RCE / RE)**: Independent non-linear and reduction hardware per lane, equipped with dedicated **24 KB Scratch SRAM buffers** (`ScratchA` and `ScratchB`), mathematical lookup tables (`LUT_exp`, `LUT_recip`, `LUT_rsqrt`) with Piecewise Linear (PWL) interpolation, and shared comparator trees supporting two-pass Softmax, two-pass Layer Normalization, and zero-area SPPF MaxPool.
* **Internal 4-Channel AXI DMA Controller & SRAM Memory Bank**: An autonomous DMA engine interfacing external DRAM across a 256-bit bus, streaming data into **~2.1 MB of on-chip physical SRAM** partitioned into 6 dedicated banks (320 KB, 320 KB, 416 KB, 408 KB, 50 KB, 50 KB) with hardware-enforced capacity clamping.
* **End-to-End ONNX Compiler Toolchain (`tools/onnx_compiler.py`)**: A Python-based automated compiler that parses standard ONNX graphs, performs dynamic shape inference, resolves memory aliases with zero compute overhead, expands broadcast dimensions, and generates C++ SystemC verification testbenches.

### 2. How has the model been verified and validated?
The verification strategy followed a rigorous hierarchical methodology comprising unit microbenchmarks, dual-lane concurrency stress tests, and automated end-to-end deep learning model benchmarks:
* **Full-Graph ONNX Model Validation**:
  * **YOLOv8m INT8 (`yolov8m-int8.onnx`)**: **261 / 261 Checkpoints Passed (100.0% Pass Rate)** across all 1,084 ONNX nodes and 23 architectural layers (`model.0` through `model.22`), achieving a Maximum Absolute Error ($\text{MAE}$) of `0.000000` and a Cosine Similarity of `1.000000`.
  * **ViT-Base INT8 (`vit_b-int8.onnx`)**: **497 / 497 Checkpoints Passed (100.0% Pass Rate)** across all 2,297 ONNX nodes and 15 major submodules (Token/Position Embeddings, all 12 Multi-Head Attention Encoder Blocks, Final LayerNorm, and Output Classification Projection), achieving an $\text{MAE}$ of `0.000000` and a Cosine Similarity of `1.000000`.
* **Microbenchmark Suite (`TC01`–`TC08`)**: Validated basic single-cycle INT8 MAC accumulation, full $64 \times 64$ tile GEMM, $3 \times 3$ sliding-window convolution, extreme numerical boundary/clamping cases, asynchronous dual-queue dispatch, dual-lane LayerNorm bank isolation (0/256 mismatches), and SPPF max-pooling comparator sharing.

### 3. What are the key results and next steps?
* **Quantitative Performance**: In cycle-approximate simulation at a target clock frequency of $1.0\text{ GHz}$, the core achieves a throughput of **1,971.9 inferences/second** on ViT-Base INT8 ($405,700\text{ cycles}$ total latency) and **388.5 inferences/second** on YOLOv8m INT8 ($2,059,200\text{ cycles}$ total latency).

### Engineering Motivations for Architectural Evolution (Rev1 $\rightarrow$ Rev2)
1. **Resolution of Execution Serialization**: In Rev1 architectures, non-linear operations (Softmax and LayerNorm) were routed through a single, shared reduction unit. When concurrent workloads were dispatched across dual lanes, processing ground to a halt due to mutual resource contention. Rev2 solves this by duplicating the reduction and reconfigurable engines into **`RCEA`/`REA` for Lane A** and **`RCEB`/`REB` for Lane B**, each provisioned with a dedicated **24 KB Scratch SRAM buffer**.
2. **Elimination of Quantization Drift**: Early prototype decoders utilized double-precision floating-point arithmetic for matrix multiplication emulation. While functionally accurate for floating-point models, this introduced numerical drift when evaluating quantized INT8 models. The v4.4 model enforces **pure signed 8-bit integer multiplication, 32-bit accumulation, and $[-128, 127]$ saturation**, ensuring 100% bit-exact correlation with physical fixed-point RTL multipliers.
3. **Hardware-Constrained DMA Protection**: Real silicon memories possess rigid physical boundary limits. Without hardware-enforced transfer bounds, large multi-head attention sequence tensors would overflow local SRAM buffers. The v4.4 DMA subsystem implements **hardware capacity clamping** across all six physical memory banks, preventing memory corruption.

### 2.1. Subsystem Functional Breakdown

#### A. Host Control & Instruction Decoder (`control/instruction_decoder.h`, `config_regs.h`)
The host CPU (an embedded Ibex RISC-V RV32EC core or host processor) configures and controls the NPU via 32-bit memory-mapped registers (MMIO). Rich 64-bit instructions are formatted via two 32-bit writes (`FX1_INST_LO` and `FX1_INST_HI`) or pushed directly to dedicated lane FIFOs (`FX1_QUEUE_A_PUSH` and `FX1_QUEUE_B_PUSH`). The decoder manages instruction lifecycle, hazard detection, bank address translation, and execution triggers.

#### B. Symmetric Dual-Lane Systolic Array Grids (`systolic_array/sa_array.h`)
Computation is centered around two symmetric systolic arrays:
* **Array Dimensions**: $32 \text{ rows} \times 64 \text{ columns}$ of Processing Elements per lane ($2,048\text{ PEs}$ per array, $4,096\text{ PEs}$ total across the chip grid of $64 \times 64$).
* **PE Microarchitecture**: Each PE contains an 8-bit $\times$ 8-bit signed integer multiplier and a 32-bit partial sum accumulator register.
* **Spatial Row Partitioning (`FX1_NSPLIT`)**: Controlled via CSR `0x40000214`. Workloads are split across the spatial boundary:
  $$\text{Lane A Rows} = [0, N_{\text{split}} - 1] \quad \text{and} \quad \text{Lane B Rows} = [N_{\text{split}}, Y_{\text{DIM}} - 1]$$
  Under default settings ($N_{\text{split}} = 32$), Lane A processes rows $0 \dots 31$, and Lane B processes rows $32 \dots 63$. Setting $N_{\text{split}} = 0$ power-gates Lane B, assigning 100% of the computation to Lane A.

#### C. Data Feeders & On-Chip SRAM Subsystem (`data_feeder/`, `sram/sram_top.h`)
Data feeders stream feature activations and stationary weights into the systolic PE array grid using double-buffered line FIFOs. The on-chip memory hierarchy consists of **~2.1 MB of localized SRAM** partitioned into 6 dedicated hardware banks to guarantee conflict-free, single-cycle concurrent accesses.

#### D. Output Post-Processing Block (OBP Epilogue Engine) (`psm/obp_top.h`)
The OBP epilogue unit operates on the drained partial sums, executing four synchronous pipeline stages across 64 parallel channels per lane:
1. **Bias Addition**: Adds 32-bit channel-specific bias values from `bias_ram[64]`.
2. **Requantization & Scaling**: Multiplies intermediate sums by a fixed-point scale multiplier and performs arithmetic right-shifting using `scale_ram[64]` and `shift_ram[64]`.
3. **Non-Linear Activation LUT**: Applies arbitrary non-linear activation functions (ReLU, Sigmoid/SiLU, GELU) using a dedicated **16 KB SRAM Activation LUT** per lane ($64\text{ channels} \times 256\text{ entries}$).
4. **Residual Skip Addition**: Performs element-wise addition with a residual skip tensor streamed from Bank 3 before saturating and clamping the result to $[-128, 127]$.

#### E. Dual Reconfigurable & Reduction Engines (RCE / RE) (`psm/re_rce.h`)
Dedicated non-linear vector acceleration engines logically separated into:
* **Reduction Engine (RE)**: Houses 64-wide combinational adder and comparator trees, an internal state machine, and a dedicated **24 KB Scratch SRAM** (`ScratchA` on Lane A, `ScratchB` on Lane B).
* **Reconfigurable Engine (RCE)**: Encapsulates non-linear mathematical lookup tables (`LUT_exp` 256 B, `LUT_recip` 512 B, `LUT_rsqrt` 2,048 B) equipped with smooth Piecewise Linear (PWL) interpolation.
* **Workloads Accelerated**: Two-pass Softmax for Transformer Multi-Head Self-Attention (`FUSED_ATTN`), two-pass Layer Normalization (`LAYERNORM`), and SPPF MaxPool (`ELEM_WISE MODE=MAX_POOL`).

#### F. Autonomous 4-Channel AXI DMA Controller (`control/sauria_dma.h`)
The DMA subsystem arbitrates burst data transfers between system DRAM and local SRAM banks over a 256-bit AXI bus. It features four dedicated read channels (CH0 for Weight A, CH1 for Weight B, CH2 for IFMap A, CH3 for IFMap B/Skip) managed via Round-Robin arbitration, alongside an independent, dedicated write master channel.

# 3. SystemC Model Architecture & Modeling Methodology

The SAURIA FX1 SystemC model is developed in standard C++17 complying with the **IEEE 1666-2023 / SystemC 2.3.3** specification. It adopts a **cycle-approximate transaction-level modeling (TLM)** style.

```
+-----------------------------------------------------------------------------------------------------------------------+

+-----------------------------------------------------------------------------------------------------------------------+
|                                                                                                                       |
|  sauria::NpuTop (SC_MODULE)                                                                                           |
|  ├── sauria::ConfigRegs<32, 32, 64, 64>            [CSR Register File & Profile Storage]                             |
|  ├── sauria::InstructionDecoder<64, 64, int8_t>    [64-bit Rich ISA Decoder, Queue A, Queue B]                       |
|  ├── sauria::SauriaDma<64, 64, int8_t>             [Internal 4-Channel AXI DMA Engine]                               |
|  ├── sauria::SramTop<64, 64>                       [6-Bank On-Chip Physical SRAM Storage (~2.1 MB)]                   |
|  ├── sauria::IfmapFeeder<64, int8_t, 1024, 16>     [Lane A & Lane B Activation Feeders]                              |
|  ├── sauria::WeiFeeder<64, int8_t, 1024, 16>       [Lane A & Lane B Weight Feeders]                                  |
|  ├── sauria::SystolicArray<64, 64, int8_t>         [Lane A & Lane B 64x64 Systolic PE Arrays]                        |
|  ├── sauria::Psm<64, 64, int32_t>                  [Lane A & Lane B Partial Sum Scanner Units]                       |

|  ├── sauria::ReconfigurableEngine<0x200000>        [Lane A & Lane B Non-Linear Mathematical LUTs]                    |
|  └── fx1::PerfCounters                             [60-Metric Hardware Telemetry & Profiling Unit]                   |
|                                                                                                                       |
+-----------------------------------------------------------------------------------------------------------------------+
```

### 3.1. Modeling Mechanics & SystemC Constructs
* **Cycle-Approximate Pipeline Execution**: The compute datapath utilizes `SC_METHOD` processes sensitive to `i_clk.pos()`. The systolic array, OBP stages, and data feeders advance their internal pipeline registers on every clock edge, exactly matching physical hardware pipeline depth and latency.
* **Asynchronous Queue Scheduling**: `SC_THREAD` processes (`queue_scheduler_a` and `queue_scheduler_b`) monitor instruction FIFO depth and trigger execution pipelines asynchronously, modeling independent concurrency between lanes.
* **Inter-Module Communication**: Point-to-point connections use strongly typed `sc_in<T>` and `sc_out<T>` ports transmitting custom structured data types (e.g., `psum_vector_t<64, int32_t>`, `act_vector_t<64, int8_t>`).
* **Event Synchronization**: DMA transfer completions and execution barriers are signaled using `sc_event` primitives, avoiding wasteful polling loops.

### 4.2. 64-bit Rich ISA Opcode Specifications
Rich instructions submitted to the decoder follow a packed 64-bit format:
```
Bit Fields:
+-------------------+-------------------+-------------------+-------------------+
|   w_addr [63:32]  |  in_addr [31:16]  |    flags [15:8]   |   opcode [7:0]    |
+-------------------+-------------------+-------------------+-------------------+
```

* **`0x05` (`SET_NSPLIT`)**: Configures the spatial row boundary dividing Lane A and Lane B and executes a hardware barrier synchronization.
* **`0x12` (`GEMM_FUSED`)**: Fused Matrix Multiplication and 2D Convolution:
  $$Y = \text{Clamp}_{\text{int8}}\Big(\text{LUT}\big(\text{Requant}(X \cdot W + \text{Bias})\big) + \text{Residual}\Big)$$
* **`0x13` (`FUSED_ATTN`)**: Fused Multi-Head Self-Attention Softmax reduction:
  $$\text{Attention}(Q, K, V) = \text{Softmax}\left(\frac{Q \cdot K^T}{\sqrt{d_k}}\right) \cdot V$$
* **`0x14` (`LAYERNORM`)**: Two-pass fused Layer Normalization:
  $$y_i = \gamma_i \cdot \frac{x_i - \mu}{\sqrt{\sigma^2 + \epsilon}} + \beta_i, \quad \text{where } \mu = \frac{1}{N}\sum_{j=1}^N x_j, \; \sigma^2 = \frac{1}{N}\sum_{j=1}^N (x_j - \mu)^2$$
* **`0x15` (`ELEM_WISE`)**: Vectorized element-wise arithmetic across 5 operational modes (Mode 0: `ADD`, Mode 1: `MAX_POOL`, Mode 2: `MUL`, Mode 3: `SUB`, Mode 4: `DIV`) with automated 1D channel broadcasting.

# 5. Key Architectural & Microarchitectural Design Decisions

### 5.1. Dataflow Architecture: Output Stationary (OS)
* **Design Decision**: The systolic array implements an **Output Stationary** dataflow.
* **Architectural Rationale**: 
  * Intermediate 32-bit partial sums remain stationary inside local PE accumulators throughout $K$ reduction iterations. Activations stream horizontally across PE rows, while weights stream vertically down PE columns.
  * Accumulating locally eliminates high-energy inter-PE wire toggles during contraction cycles, preserving 32-bit precision before single-pass requantization down to 8-bit signed integers in the OBP epilogue pipeline.

### 5.2. On-Chip Physical SRAM Banking (~2.1 MB)

> **Total Physical On-Chip SRAM Capacity**: **~2.1 MB** (2,129,920 Bytes working footprint)

### 5.3. Double Buffering & DMA Memory Clamping
The AXI DMA engine runs concurrently with the systolic execution datapath. While the PE array computes tile $T_k$, the DMA controller prefetches weights and activations for tile $T_{k+1}$ into alternate SRAM buffers. To prevent memory corruptions from misaligned compiler instructions, all DMA transfer sizes are explicitly clamped to the physical capacity of the target SRAM bank.

# 6. Verification, Validation, and Toolchain Framework

### 6.1. Automated ONNX Compiler Toolchain (`tools/onnx_compiler.py`)
The automated compiler bridges high-level deep learning frameworks with low-level SystemC execution:
1. **Dynamic Graph Parsing & Shape Inference**: Recursively traces the ONNX computational graph, inferring dynamic tensor shapes and data types directly from node attributes.
2. **Zero-Compute Node Aliasing**: Identifies shape transformation nodes (`Reshape`, `Transpose`, `Flatten`, `Squeeze`, `Unsqueeze`, `Identity`, `Concat`, `Split`, `Slice`, `QuantizeLinear`, `DequantizeLinear`) and aliases their memory addresses directly, incurring **0 compute instructions and 0 DRAM copy overhead**.
3. **1D Channel Bias Broadcasting**: Automatically tiles 1D bias parameters to match 2D feature map dimensions without duplicating DRAM weight memory.
4. **C++ Testbench Generation**: Emits standalone, self-contained SystemC testbenches (`test_onnx_model.cpp`) and packed initialization binary payloads (`dram_init.bin`, `golden_ref.bin`).

### 9.3. Architectural Discussion on Zero-Value Performance Counters
* **`reshape_engine_cycles = 0`**: In the SAURIA architecture, tensor transformations (`Reshape`, `Transpose`, `Concat`, `Split`) are performed via **zero-overhead compiler address aliasing**, executing with 0 hardware cycles.
* **`memory_wait_cycles = 0` & `pipeline_bubble_cycles = 0`**: On-chip SRAMs feature dedicated single-cycle ports for IFMap and Weight feeders with double buffering, preventing bank collision stalls.
* **`ddr_stall_cycles = 0`**: The high-level virtual prototype models DRAM transfers with cycle-approximate burst counts, assuming ideal DDR channel response without arbitration stalls.

| :--- | :--- | :--- |
| **1. # 12. Current Model Limitations, Assumptions & Known Issues

1. **Virtual DRAM Latency Model**: DRAM access latency is modeled with cycle-approximate burst calculations rather than full cycle-accurate DDR controller arbitration backpressure.
2. **2D Bilinear / Nearest-Neighbor Resize**: Bilinear and nearest-neighbor upsampling are handled via compiler index lowering; a dedicated hardware 2D `Resize` interpolation unit is targeted for the next hardware revision.
3. **Physical Power Modeling**: The current prototype reports cycle and bandwidth utilization; physical dynamic power and thermal modeling are not included in the SystemC model.

**Date**: September 14–15, 2026  
**Target Core**: SAURIA NPU Neo Core Lite 32 (`v4.2_model`)  
**Scope**: Reduction Engine Wiring Fix, Simulation Performance Acceleration, Native Thread Full-Model Regression (YOLOv8m & ViT), and Component Specifications.

## 1. Executive Summary

This update resolves a hardware signal routing issue where the **Reduction Engine (RE)** output streams (`s_re_vector_out_a/b`, `s_re_valid_out_a/b`) were unconnected in the top-level SystemC wrapper ([`npu_top.h`](npu_top.h)). 

With multiplexed output logic implemented, data streams seamlessly through OBP and RE into SRAM C. In addition, simulation runtime has been significantly accelerated by setting `#define SAURIA_DEBUG 0` in [`debug.h`](debug.h). The full native hardware regression suite (`make check`) and full-graph ONNX benchmarks (`test_yolo` and `test_onnx_model`) have passed with **100% SUCCESS**.

## 2. Key Architecture Updates & Bug Fixes

### A. Hardware Defect Resolution: Reduction Engine (RE) Output Multiplexing
* **Issue Identified**: In [`npu_top.h`](npu_top.h), RE instances (`re_inst_a` and `re_inst_b`) were instantiated, but their output signals were left floating. SRAM controllers were hardwired directly to OBP outputs, bypassing RE reduction passes (LayerNorm, Softmax, MaxPool).
* **Fix Implemented**:
  1. Added multiplexed write-back signals: `s_final_sramc_wdata_a/b` and `s_final_sramc_wren_a/b`.
  2. Implemented `obp_ctrl_mux_logic`: Drives OBP vector outputs (`s_obp_sramc_wdata_a/b`) into `s_re_vector_data_a/b`.
  3. When `s_re_mode_a/b != RE_MODE_IDLE`, the SRAM controller write bus dynamically selects `s_re_vector_out_a/b` and `s_re_valid_out_a/b`.

### B. Simulation Performance Acceleration
* **File Updated**: [`debug.h`](debug.h)
* **Change**: Changed default macro `#ifndef SAURIA_DEBUG` from `1` to `0`.
* **Impact**: Suppressed excessive per-cycle console printouts during multi-million-cycle full-model simulations, speeding up simulation execution time by several orders of magnitude.

### C. Execution Thread Model Clarification (Native Thread vs. Instruction Decode)
* **Native Thread (`NpuTop<32, 32, ...>`)**: Direct cycle-accurate execution of SystemC hardware modules (`SystolicArray`, `Obp`, `ReconfigurableEngine`, `ReductionEngine`, `Psm`, `Sram`).
* **Instruction Decoder (`InstructionDecoder`)**: Translates 64-bit Rich ISA opcodes into control signals for hardware blocks.
* **Verification Scope**: Native thread simulation verifies cycle-level physical data transfers and hardware block pipeline alignment.

### D. Hardware Defect Resolution: OBP Bias Register Saturation (`0x80000000` / `2147483648`)
* **Issue Identified**: When loading negative bias values via `FX1_OBP_A_BIAS_BASE` (`0x00150000` for Lane A, `0x00170000` for Lane B) (such as `adj_bias[0] = -65002` for OC-tile 0, or `adj_bias[0] = -51331` for OC-tile 1), reading back immediately from the register always returned fixed `2147483648` (`0x80000000`). This caused severe layer calculation errors because the hardware stored and added `-2147483648` to every output channel during bias fusion.
* **Root Cause**: `host_data_t` stores MMIO data words as `double`. In the host write wrapper (`wr(addr, val)`), `val` is `uint32_t` (e.g., `(uint32_t)-65002 = 4294902294`). When passed into `wdata[0]`, it became `4294902294.0`. In [`psm/obp_top.h`](psm/obp_top.h), `bias_ram[lane_idx] = static_cast<int32_t>(wdata[0]);` was executed. Because `4294902294.0 > INT32_MAX` (2,147,483,647), x86 `cvttsd2si` instruction saturated directly to the indefinite 32-bit integer `0x80000000` (`-2147483648` signed, or `2147483648` unsigned).
* **Fix Implemented**: In [`psm/obp_top.h`](psm/obp_top.h), cast `wdata[0]` via `int64_t` -> `uint32_t` -> `int32_t`:
  ```cpp
  int64_t val64 = static_cast<int64_t>(wdata[0]);
  bias_ram[lane_idx] = static_cast<int32_t>(static_cast<uint32_t>(val64));
  ```
  Scale and shift parsing were also updated with `int64_t` intermediate casts to prevent integer truncation or overflow on wide unsigned multipliers.

### E. Hardware Defect Resolution: OBP Scale and Shift Address Decoding in `host_rdata_mux`
* **Issue Identified**: In [`npu_top.h`](npu_top.h), reading back scale (`0x00180000` / `0x001A0000`) and shift (`0x00190000` / `0x001B0000`) registers returned incorrect data.
* **Root Cause**: In `host_rdata_mux()`, scale and shift address regions were missing from the condition checks (only `0x00140000`/`0x00150000` for Lane A and `0x00160000`/`0x00170000` for Lane B were checked). Read requests to scale and shift regions fell through to `s_host_rdata_sram`.
* **Fix Implemented**: In [`npu_top.h`](npu_top.h), decoded scale and shift address regions in `host_rdata_mux()`:
  ```cpp
  else if (region == 0x00140000 || region == 0x00150000 || region == 0x00180000 || region == 0x00190000)
  {
      o_host_rdata.write(s_host_rdata_obp_a.read());
  }
  else if (region == 0x00160000 || region == 0x00170000 || region == 0x001A0000 || region == 0x001B0000)
  {
      o_host_rdata.write(s_host_rdata_obp_b.read());
  }
  ```
